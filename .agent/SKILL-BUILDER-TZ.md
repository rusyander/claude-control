# Задача 2. Готовые тестовые запросы в песочнице

## Что не так сейчас

Чипы с подсказками есть, но они общие по типу элемента: для любого скилла
предлагается «Какие скиллы тебе доступны?». Это не проверяет конкретный скилл —
проверяет, что список скиллов вообще существует. Пользователю приходится
дописывать запрос руками.

## Решение

Тестовый запрос собирается **из самого элемента**, а не берётся из общего списка.

| Тип          | Откуда берётся запрос                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Скилл        | Из `description` — там написано «Use КОГДА …», то есть прямо описан случай, в котором скилл должен сработать. Превращаем условие в задачу. |
| Правило      | Из заголовка и текста правила: правило запрещающее → запрос, провоцирующий запрет; правило про формат → запрос, где формат проявится.      |
| Хук / скрипт | Из события и фильтра: PreToolUse+Bash → команда через Bash; PreToolUse+Write → запись файла.                                               |
| MCP          | Из имени первого инструмента сервера.                                                                                                      |
| Группа       | Перечисление подключённого + провокация по самому «строгому» члену.                                                                        |

Чип показывает короткую подпись, вставляет полный запрос. Рядом — кнопка
копирования (уже есть).

## Крайние случаи

- У скилла пустой `description` → общий запрос по имени скилла.
- У правила только заголовок → запрос из заголовка.
- Событие хука без фильтра (SessionStart, Stop) → запрос, вызывающий начало
  работы, плюс пометка, что событие может не проявиться в одном ответе.
- MCP не отвечает → чип всё равно есть, но помечен как непроверенный.

# Задача 1. Конструктор скиллов

## Что требуется

1. Редактировать каждый файл скилла, а не только смотреть.
2. Создавать вложенную структуру: папки и файлы на любом уровне.
3. Форма-конструктор при создании скилла — с деревом и добавлением узлов.
4. Работать на скиллах любого размера: от одного файла до сотен.
5. Помощник должен понимать всю структуру и заполнять её целиком.
6. Результат проверяется в песочнице.

## Разбор вариантов раскладки

**А. Список форм подряд (как предложил пользователь).**
Каждый файл — своя форма, всё на одном экране со скроллом.
_За:_ видно всё сразу, просто. _Против:_ при 50+ файлах экран нечитаем,
скролл на тысячи пикселей, браузер тормозит на сотнях редакторов сразу,
неясно, где находишься. **Отклоняю для больших скиллов.**

**Б. Дерево слева + редактор справа (как в редакторе кода).**
_За:_ стандарт, узнаваем, масштабируется до любого числа файлов, в памяти
один редактор. _Против:_ видно один файл за раз.
**Выбираю как основу.**

**В. Гибрид: дерево + редактор + режим «показать все файлы подряд».**
Основной режим — Б, но есть переключатель на сплошной просмотр для мелких
скиллов и для вычитки целиком. **Беру: Б с опциональным режимом В.**

## Модель данных

Черновик скилла расширяется с трёх полей до дерева:

```
SkillDraft {
  name, description,          // frontmatter SKILL.md
  body,                       // тело SKILL.md
  files: [{ path, content }]  // всё остальное, путь от корня скилла
}
```

Папки отдельными сущностями не хранятся — они выводятся из путей файлов,
как и сейчас на чтении. Пустая папка невозможна, и это правильно: скилл из
пустых папок бесполезен.

## Серверная часть

- `GET /api/skills/:id/file?file=` — чтение (уже сделано).
- `PUT /api/skills/:id/file` — запись одного файла, с бэкапом.
- `DELETE /api/skills/:id/file?file=` — удаление файла или папки целиком.
- `POST /api/skills/:id/file` — создание файла (в том числе в новой папке).
- Сохранение скилла целиком принимает `files` и пишет их пачкой.

Защита во всех: путь нормализуется и проверяется, что он остаётся внутри
папки скилла; отказ на выход наружу. Размер файла ограничен.

## Интерфейс конструктора

Модальное окно размера `xl`, три части:

1. **Слева — дерево** с кнопками «новый файл» и «новая папка» на каждом
   уровне, переименованием и удалением. Файл с несохранёнными правками
   помечается точкой.
2. **Справа — редактор** активного файла: имя, содержимое, для SKILL.md
   отдельные поля frontmatter.
3. **Внизу — помощник** (как в остальных формах).

## Помощник в конструкторе

Ключевое отличие от прочих форм: он заполняет не набор полей, а **структуру**.
Схема, которую он получает:

```
name, description, body — как раньше
files — массив { path, content }
```

Помощник умеет: создать структуру с нуля по описанию задачи, разложить один
большой SKILL.md на модули, дописать недостающий файл, переписать конкретный
файл. Применение результата — слияние: существующие файлы обновляются,
новые добавляются, ничего не удаляется без явного действия пользователя.

## Шаблоны структуры

При создании предлагаются заготовки, чтобы не начинать с пустоты:

- **Простой** — только SKILL.md.
- **С референсами** — SKILL.md + `references/` на несколько тем.
- **Полный** — SKILL.md + `references/` + `config/` + `templates/`.
  (Форма скиллов вроде `frontend-architecture`: тонкий вход и модули по темам.)

## Крайние случаи

- **Сотни файлов**: дерево виртуализируется, редактор один.
- **Двоичные файлы** (картинки в assets): показываем как «двоичный файл»,
  не даём редактировать текстом, но позволяем удалить.
- **Огромный файл** (>512 КБ): не открываем, предупреждаем.
- **Конфликт имён**: при создании файла с существующим именем — предупреждение.
- **Правка вне приложения**: при открытии показываем актуальное с диска.
- **Отмена**: закрытие с несохранёнными правками спрашивает подтверждение.

## Порядок работ

1. Тестовые чипы в песочнице (задача 2) — быстрая победа.
2. Серверные маршруты файлов скилла.
3. Дерево с редактированием и созданием.
4. Помощник по структуре и шаблоны.
5. Проверка: создать многоуровневый скилл через конструктор, проверить его
   в песочнице, убрать за собой.
