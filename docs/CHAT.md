# Chat, tabs and parallel agents

Not a separate bot and not an API wrapper: the same `claude` you run in the terminal, with the conversation kept in ordinary Claude Code transcripts. A chat started in the terminal shows up in the panel, and the other way round.

## Concurrency: a tab is a project and its process

Each project gets its own tab and its own process, and switching tabs does not stop an agent.

- **The dot on the tab.** Green — working, yellow — waiting on an answer, red — an error, a limit, or a stall (two minutes without events). A background agent that finished or hit a question sends a notification; clicking it opens that project.
- **Edits are allowed by default,** and the toggle remembers its position — check it before handing a task to an unfamiliar repository. A stalled run offers "Retry" and "Allow and continue"; the second replays the request with full access, bypassing both the toggle and the Permissions section.
- **Spend is visible immediately** — in tokens by default, because on a subscription dollars mean nothing; switch to money in Settings.
- **A run belongs to the server, not to the tab.** Closing the tab or hitting F5 only detaches a listener; the panel re-attaches to live runs, and a run that finished while the tab was closed makes it back into the feed within a grace minute, after which it lives only in the transcript. Session spend is counted server-side too. The real boundary is a server restart: the run registry lives in its memory.

## The dev server, straight from the tab

**A project tab is its dev server too.** "Start" takes the command from `package.json` (`dev`, otherwise `start`) or your own and runs it with the package manager the project actually uses — pnpm, yarn or npm, read from `packageManager` and the lock file. **The panel does not assign the port:** the app comes up on its own, and the panel reads the address from the output, opening the browser once the port answers. A monorepo has several targets — the gear lists the root and the packages, and they run at the same time. If a port is taken, the panel shows who holds it (name and PID) and offers to free it; it kills nothing on its own. "Autostart" brings a target up on the panel's _next_ start, **with no browser window and no navigation**; close the tab and it clears on all targets.

## Project git

**Branch, files, commit and pull right there,** whenever the project has a `.git` (no `.git`, no section at all): the button carries the current branch, the number of changed files and how far behind the remote you are; under it sit the changed files, the local branches, the `pull` row, a new-branch field and a commit message field. `pull` goes into the current branch through its upstream, or from a chosen remote branch; it is the operation that may merge — the panel neither resolves nor rolls back a conflict, git's own text reaches you as is. `push` sends the current branch, setting the upstream on its first run; nothing is forced, and a rejected push comes back with git's own words. No branch deletion, no force: this is not a git client, only what you need while an agent works in the repository. Under the hood: `git` with no shell, branch names validated by `git check-ref-format`, checkout and pull limited to names on the list, so a stray ref cannot walk HEAD into detached state.

## A branch per agent: parallel copies

The git section has "Parallel copies": the button creates a working copy (`git worktree`) on a new or existing branch under `<repository>-worktrees/<branch>` next to the project — never inside it, where watchers and bundlers would recurse into the copy — and opens it as an ordinary project tab, so status dots, the agents dock and the chat list work there with no special case. The branch is re-read from git every time: the agent inside is free to switch, and a remembered name would lie. A copy with a live agent cannot be removed, and there is no merging in the panel at all — that stays with you.

## The first edit asks where to work

A chat is bound to a directory, not to a branch, and git gives a project one directory for all of its chats. While the agent only reads, nobody minds; the first edit makes the chats depend on each other — they touch the same files, and a `checkout -b` in one moves the branch under all the others. So before the first edit **in the main working copy** the panel holds the call and shows a card: a branch name (proposed from the task, editable in place) and three answers — "create the copy and continue there", "write here", "do not edit".

"Create the copy" does exactly that: a `git worktree` on that branch off the current HEAD, next to the project, and **the same chat** moves there — the run is restarted with `--resume`, so the history, the task and the link to the conversation stay as they were, and the main directory is not touched at all. From then on the chat treats the copy as home by itself: the panel reads a conversation's working directory from the last transcript record. A refusal from git (a name already taken, a repository with no commits) does not dismiss the card — the edit stays held all along, so fixing the name and pressing again is enough.

"Write here" answers for the whole run rather than for one file: the next edit does not bring the card back. The next message into that chat asks again — the conversation starts in the main copy once more, and there is nothing to keep quiet about.

The gate sits on the permission wire, not in a prompt, so nothing slips past it — neither Claude Code nor a foreign CLI: edit tools are recognised by the names every supported CLI uses, and a shell write by the command itself (`>`, `tee`, `sed -i`, `git apply`, `cp`). Parsing the command is coarse on purpose: an extra card costs one click, a missed one costs an edit in the shared copy. What the gate does **not** catch is stated in [Limitations](LIMITATIONS.md).

One toggle in the permissions turns it off — "Edits in the project main copy": with the rule on, every chat of the project writes wherever it is open, as before. In a copy, in the sandbox and in a directory with no `.git` the gate keeps quiet on its own — there is nothing to share there.

## Splitting a list of tasks across chats

Give the agent several independent tasks and the answer comes back with a proposed split; in place of the service block the panel draws a card: "do them here in turn" or "split into N chats". The second creates a branch with a copy and a chat per group, each already carrying its slice; a "create the chats only" checkbox puts the task into the composer instead of starting the runs. No sub-agents anywhere — you talk to each chat yourself. The agent's initiative is a setting, and the composer's "Split tasks" button asks for a split at any moment. A project without a `.git` gets chats with no copies, in the same directory, and one failed group never cancels the rest — the card reports what actually started. It works with the other CLIs too, because the channel is text inside the answer rather than a Claude-only tool.

A group bound to the project switches itself on in the spawned chats as well: a branch copy counts as the same project — see [Groups](GROUPS.md).

## Continuing in a clean session — the panel's own `/clear`

A conversation gets more expensive with every turn: the whole context window goes to the model on each request, so once a task is done you keep paying for a conversation nobody needs. The CLI cures that with `/clear`, but neither the model nor a hook can call it — it lives on the client side. The panel owns the process, so a "clean session" here is a run without `--resume`: a new conversation in the same directory and the same branch that knows exactly what the checkpoint file (`.agent/PROGRESS.md`) says.

Having closed a task, the agent first tidies its working files — closed items out of PROGRESS, finished ones out of `TASKS.md`, each moved to `.agent/ARCHIVE.md` as a single line — and only then offers the move as a card: what is closed, what was pruned and the full task for the new session. Two buttons, both legitimate: "continue in a new chat" and "stay here". The old conversation stays where it was.

The "keep going on your own" toggle enables auto-continue **for that conversation**: from then on the panel moves by itself, but the decision is the server's rather than the tab's — the chain survives a closed browser — and a conversation continues at most eight times in a row. Out of the box the automation is on: a chain with nobody at the panel is the point of working overnight, and the safeties keep it in its banks. Two of them stop it early: a failed run is never continued, and if the checkpoint file is word for word the one from the previous handover, the panel stops — the agent is going in circles. The agent may also ask in prose: "restart the session", "/clear", "continue from .agent/PROGRESS.md" at the end of an answer is read exactly like the block. Need the switch right now — "Перезапустить сессию" in the header menu: a fresh checkpoint opens the new conversation at once, a stale one gets the agent asked to write it. Turn the automation off per conversation with the toggle, or everywhere in Settings → "Продолжать самой во всех разговорах"; one switched off by hand stays off. **Other CLIs do all of this too**, with one difference stated out loud: they have no session, so a continuation is a NEW conversation in the same directory carrying the checkpoint and the original task, not a return to the same place. The same tidying rule ships as a ready-made skill template in the Skills section, for anyone who wants order in the working files without any handover at all.

## What the chat does not do

| What                                                                           | Why                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A run finishing while the page is closed waits one minute                      | **by design.** The buffer holds it for a grace minute; later it lives only in the transcript                                                                                                                                                                                                                                                                                    |
| Conversations cannot be deleted or renamed                                     | **by design.** Transcripts belong to Claude Code; the panel only reads them                                                                                                                                                                                                                                                                                                     |
| Full-text search over messages is bounded                                      | **by design.** To avoid reading gigantic transcripts whole, matches and files scanned are capped                                                                                                                                                                                                                                                                                |
| The feed opens at the latest messages                                          | **by design.** Earlier ones arrive via "Load more"                                                                                                                                                                                                                                                                                                                              |
| The created-files list exists only for chats outside a project                 | **by design.** Inside a real repository it is useless                                                                                                                                                                                                                                                                                                                           |
| Per-item permissions do nothing in full-access mode                            | **by design.** Everything is allowed there by definition                                                                                                                                                                                                                                                                                                                        |
| Project git has no branch deletion, no merge, no conflict resolution           | **by design.** The panel is not a git client; it does exactly what you need while an agent works in the repository: branch, switch, new branch, commit, `pull` and `push`. A conflict left by `pull` is not resolved here — that is terminal work                                                                                                                               |
| A commit takes every change (`git add -A`)                                     | **by design.** There is no file picking and no index editing in the panel — git is for that                                                                                                                                                                                                                                                                                     |
| The panel does not assign the dev server's port — it reads it from the output  | **by design.** `PORT` is ignored by everything that keeps the port in its config. A server that prints no address runs without a link — pin its port by hand                                                                                                                                                                                                                    |
| Freeing a busy port kills a process by PID, and only on a button press         | **by design.** A database or a neighbouring project may live there: the panel shows who it is, the person decides                                                                                                                                                                                                                                                               |
| Parallel copies are created and removed here, never merged                     | **by design.** Merging stays with you. A copy lives beside the repository (`<repository>-worktrees/<branch>`), only a path git itself listed can be removed, and only while no agent works inside it — otherwise 409                                                                                                                                                            |
| The first-edit gate is a default, not a sandbox                                | **by design.** Edit tools are recognised by the names every supported CLI uses, a shell write by the marks of the command (`>`, `tee`, `sed -i`, `git apply`, `cp`); an edit taking a back road — a script of its own, an editor launched from inside a command — walks past. Forbidding edits is the permissions section's job; the gate only moves the work into its own copy |
| The gate does not separate two chats sitting in one copy                       | **by design.** The question is asked in the main working copy only: a copy already has a branch of its own, and the panel does not take it upon itself to divide that. A directory with no `.git`, and the sandbox, get the same silence                                                                                                                                        |
| Task fan-out: at most 8 groups and 50 tasks each, and no chat opens on its own | **by design.** The proposal comes out of the model's answer rather than a form, so it is capped; the split is started by a person on the card, and only the latest proposal in the feed is actionable                                                                                                                                                                           |
| One group failing during a fan-out rolls nothing back                          | **by design.** The card reports what actually started; a project without a `.git` gets chats with no copies, in the same directory                                                                                                                                                                                                                                              |
| Continuing in a clean session works inside a project only                      | **by design.** The new session is created in the closed conversation's directory; the sandbox has none, so the card stays read-only                                                                                                                                                                                                                                             |
| The auto-continue toggle does not survive a server restart                     | **by design.** It lives in the server's memory next to the run registry; its default comes from the "Продолжать самой во всех разговорах" setting, and a conversation continues at most eight times in a row                                                                                                                                                                    |
| The automation refuses when the checkpoint was not updated in that same run    | **by design.** The clean session reads exactly that file: continuing from yesterday's state is lost work, not saved money. The refusal is explained by a toast                                                                                                                                                                                                                  |
| The old context is not carried into the new conversation                       | **by design.** That is the whole point: the new session knows exactly what the agent wrote into the checkpoint. The previous conversation stays in the list in full                                                                                                                                                                                                             |
