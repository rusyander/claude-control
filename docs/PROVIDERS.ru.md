# Провайдеры: детали форматов

Расшифровка сносок из карты «раздел × провайдер» — она в
[README.ru.md](../README.ru.md#другие-cli-кроме-claude). По каждой строке карты: где лежит файл,
что панель в нём правит, чего не трогает и почему статус именно такой. Всё — по официальной
документации CLI и по коду адаптеров.

Инструменты, которые работают поверх провайдеров (перенос окружения, каталог моделей, проверка на
вашей машине, предпросмотр записи, сравнение и сверка форматов со схемами), — в
[Провайдеры: инструменты панели](PROVIDER-TOOLS.ru.md).

## 1. Глобальные инструкции

Обычный markdown, раздел переносится один в один: `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`,
`~/.gemini/GEMINI.md`, `~/.qwen/QWEN.md`, `~/.config/opencode/AGENTS.md`,
`~/.config/goose/.goosehints`, `~/.kimi-code/AGENTS.md` (каталог переносится `KIMI_CODE_HOME`).

**Goose — тот же обычный файл, но под Windows другой путь.** Подсказки лежат в `.goosehints` рядом
с конфигурацией, а сама конфигурация не в `~/.goose`: на macOS и Linux это `~/.config/goose/`, под
Windows — `%APPDATA%\Block\goose\config\`. В проекте файл называется `<проект>/.goosehints`.

**Cursor — каталог, а не файл.** `~/.cursor/rules/*.mdc`, каждый файл — правило с YAML-frontmatter
(`description`, `globs` через запятую, `alwaysApply`) и markdown-телом; подкаталоги
поддерживаются. Раздел стал менеджером каталога: список, создание, правка, удаление; три поля
frontmatter — отдельными полями формы, тело пишется дословно, чужие ключи frontmatter и
комментарии остаются. Обычный `.md` Cursor в этом каталоге не читает — такие файлы показаны
отдельным списком и никогда не правятся. Путь обязан лежать внутри каталога: `..`, абсолютный
путь, чужое расширение и символическая ссылка отклоняются одинаково на чтении, записи и удалении.

**Continue — глобальных инструкций нет.** Задокументирован только каталог правил ПРОЕКТА
(`<проект>/.continue/rules/*.md`), а ключ `rules:` в `config.yaml` неоднороден: там вперемешку
строки-правила и ссылки на правила хаба (`uses:`). Угадывать, что из этого «глобальные
инструкции», панель не стала — раздел скрыт, а не помечен «в разработке». Проектные правила при
этом полноценны: тот же менеджер каталога, что у Cursor, но расширение `.md`, а свои ключи шапки
Continue (`name`, `globs`, `alwaysApply`, `regex`) сохраняются. Файл без frontmatter остаётся
только для чтения.

**Aider — список ссылок.** Единого файла инструкций нет, файлы контекста перечисляются опцией
`read` в `.aider.conf.yml` (`read: [CONVENTIONS.md, anotherfile.txt]`). Раздел управляет списком:
добавить, убрать, переставить; запись через Document API `yaml`, комментарии и прочие ключи целы.
Содержимое перечисленного файла тоже открывается на правку — но только если он существует: панель
не создаёт файлы и не открывает то, на что конфиг не ссылается.

## 2. MCP-серверы

`~/.codex/config.toml` (`[mcp_servers]`), `~/.gemini/settings.json`, `~/.qwen/settings.json`,
`~/.cursor/mcp.json`, `~/.config/opencode/opencode.json` (ключ `mcp`, своя форма
`local`/`remote`).

**Continue — единственный СПИСОК.** В `~/.continue/config.yaml` ключ `mcpServers` это не карта
«имя → запись», а массив, у каждой записи имя лежит внутри полем `name`. Транспорт задаёт `type`
(`stdio` по умолчанию, `sse`, `streamable-http`), заголовки удалённого сервера —
`requestOptions.headers`. Панель правит только этот блок: прочие ключи файла (модели, правила,
контекст) и комментарии вне блока целы, незнакомые поля записи (`cwd`, таймауты, ключи) переносятся
по значению. Новый удалённый сервер получает `streamable-http` (основной по документации), а уже
записанный `sse` не переписывается. Отдельные **файлы-блоки** `mcpServers/*.yaml` (шапка
`name` / `version` / `schema: v1` и свой список `mcpServers`) Continue грузит вместе с основным
конфигом — панель показывает их в том же списке, помечая, из какого файла запись, и правит её там же.
Новые серверы по-прежнему уходят в `config.yaml`: своих файлов-блоков панель не заводит. Блок,
который она не разобрала (ссылка `uses:` вместо записи, повтор имени), пропускается целиком — с
названием файла и причиной. Проектный MCP — `<проект>/.continue/mcpServers/mcp.json` и файлы-блоки
той же папки.

**Goose — серверы вперемешку с расширениями самого CLI.** В `config.yaml` ключ `extensions` —
карта «имя → запись», и рядом с внешними MCP-серверами там лежат **встроенные расширения Goose**
(`developer`, `memory`, …). Вид записи задаёт `type`: серверами панель считает `stdio`
(`cmd` + `args` + `envs`), `sse` и `streamable_http` (адрес в `uri`, заголовки в `headers`).
Остальное (`builtin`, `platform`, `frontend`, `inline_python`) не показывается и не правится, а
любая запись поверх такой записи отклоняется — встроенное расширение через панель нельзя ни
затереть, ни переименовать в него, ни удалить. Новой записи выставляется `enabled: true` (без него
Goose сервер не поднимет), чужой `enabled: false` панель не отменяет, новый удалённый сервер
получает `streamable_http`, а уже записанный `sse` не переписывается. Прочие ключи файла
(провайдер, модель, `GOOSE_MODE`) и комментарии вне правящейся записи целы; комментарии ВНУТРИ
правящейся записи — нет: она пересобирается из значений, зато немоделируемые поля (`timeout`,
`cwd`, `env_keys`, `bundled`, `available_tools`) переносятся полностью.

**Kimi Code — MCP в ОТДЕЛЬНОМ файле.** Не в `config.toml`, а в `~/.kimi-code/mcp.json` (в
`config.toml` от MCP остаются только таймауты). Форма обычная — карта `mcpServers`, адрес
удалённого сервера в `url`. Проектный файл — `<проект>/.kimi-code/mcp.json`. Незнакомые поля
записи (`enabled`, таймауты, фильтры инструментов) переносятся по значению.

У **Aider** настройки MCP нет в справочнике опций — не «не успели», а нечего настраивать.

## 3. Переменные окружения

| CLI       | Где                                                                         |
| --------- | --------------------------------------------------------------------------- |
| Codex     | `[shell_environment_policy.set]` в `config.toml`                            |
| Aider     | ключ `set-env` в `~/.aider.conf.yml` и в проектном `.aider.conf.yml`        |
| Gemini    | `.env` — глобальный `~/.gemini/.env`, проектный `<проект>/.gemini/.env`     |
| Qwen Code | `.env` — глобальный `~/.qwen/.env`, проектный `<проект>/.qwen/.env`         |
| Continue  | `.env` — глобальный `~/.continue/.env`, проектный `<проект>/.continue/.env` |

Карты «задать переменную» в `settings.json` у Gemini действительно нет. Файл `.env` правится
построчно: меняются только строки затронутых переменных, комментарии, пустые строки и порядок
остаются как были.

**Goose — раздела тоже нет.** Своего `.env` у него не бывает: ключи хранятся в связке ключей ОС
или в `secrets.yaml`, а секреты панель не ведёт. Поэтому раздел скрыт, а не помечен «в разработке».

**Kimi Code — раздела нет.** Своего `.env` он не читает: ключи провайдеров лежат прямо в
`config.toml` (`[providers.*]`), а секреты в чужие конфиги панель не пишет.

**OpenCode — раздела нет и не будет.** По документации он умеет только подстановку
`{env:ПЕРЕМЕННАЯ}` внутри `opencode.json`, то есть читает уже заданное окружение процесса, а
своего `.env` не загружает. Создавать файл, который никто не прочтёт, панель не станет — поэтому
раздел скрыт, а не помечен «в разработке».

## 4. Права / аппрувы

- **Codex** — два корневых ключа `config.toml`: `approval_policy` и `sandbox_mode`.
- **Gemini** — `settings.json`: режим `general.defaultApprovalMode` (`default` — спрашивать всегда,
  `auto_edit` — правки файлов без вопросов, `plan` — только чтение) плюс списки `coreTools`
  (разрешено) и `excludeTools` (запрещено, сильнее). Режим `yolo` панель не записывает: по
  документации он допустим только как флаг командной строки, а в `settings.json` валит запуск CLI.
- **Qwen Code** — `settings.json`, но ключи СВОИ, не гемини-совские, хотя это его форк: режим
  `tools.approvalMode` (`default`, `plan`, `auto-edit`, `auto`, `yolo`) плюс три списка правил
  `permissions.allow` (без вопроса), `permissions.ask` (всегда спрашивать) и `permissions.deny`
  (запрет, сильнее остальных и действует даже в автономных режимах). Правило пишется как
  инструмент с уточнением: `Bash(git push *)`, `Read(/src/**)`. Здесь `yolo` панель ЗАПИСЫВАЕТ —
  у Qwen это задокументированное значение файла настроек, а не только флаг CLI. Устаревшие
  `tools.core` / `tools.allowed` / `tools.exclude` панель не пишет (документация мигрирует их в
  `permissions.*`), но сохраняет, если они уже есть в файле.
- **Continue** — ОТДЕЛЬНЫЙ файл `~/.continue/permissions.yaml` и
  три списка верхнего уровня — `allow` (выполнять сразу), `ask` (спрашивать), `exclude` (спрятать
  инструмент от агента). Режима-переключателя нет вовсе. Правило — строка вида `Read(**)`,
  `Bash(git status)`. Пустой список удаляет свой ключ, комментарии и чужие ключи файла целы. По
  документации эти права относятся к неинтерактивным запускам CLI `cn`; интерактивный режим
  спрашивает сам.
- **Cursor** — ключ `permissions` в `~/.cursor/cli-config.json` (в проекте файл называется иначе —
  `<проект>/.cursor/cli.json` — и держит только права) и ровно ДВА списка: `allow` (выполнять без
  вопроса) и `deny` (запрещено). Ни режима-переключателя, ни списка «спрашивать» у этой модели нет:
  то, что не попало ни в один список, CLI спросит сам, а `deny` сильнее `allow`. Формы правил —
  `Shell(команда)`, `Read(путь)`, `Write(путь)`, `WebFetch(домен)`, `Mcp(сервер:инструмент)`, внутри
  допустимы шаблоны `*`, `**`, `?`. Панель правит только ключ `permissions`: версия, настройки
  редактора и всё прочее в том же файле остаются нетронутыми, пустой список удаляет свой ключ.
- **Goose** — самая короткая модель из восьми: ОДИН скалярный ключ корня `config.yaml` —
  `GOOSE_MODE` (ключи настроек у этого CLI именуются как переменные окружения). Задокументированные
  значения: `auto` (действует без вопросов), `approve` (спрашивать про каждое действие),
  `smart_approve` (спрашивать про рискованное) и `chat` (только разговор, без инструментов).
  Списков правил у модели нет вовсе. Пофайловые разрешения инструментов Goose держит в отдельном
  `permission.yaml`: панель **показывает** их тремя списками («выполнять сразу», «спрашивать», «не
  выполнять»), но не пишет — формата этого файла в документации Goose нет, задокументированы лишь
  сами три уровня и настройка через `goose configure`. `secrets.yaml` и связку ключей ОС панель не
  трогает тем более.
- **Kimi Code** — вторая TOML-модель после Codex, и сразу из двух частей: корневой скаляр
  `default_permission_mode` (`manual` — спрашивать всегда, `auto` — решает агент, `yolo` — не
  спрашивать вовсе) и УПОРЯДОЧЕННЫЙ массив таблиц `[[permission.rules]]`, у каждой ровно
  `decision` (`allow` / `ask` / `deny`) и `pattern` (`Read`, `Bash(git push*)`,
  `mcp__сервер__инструмент`). Порядок значим — правила проверяются сверху вниз. Любое чужое поле
  внутри `[permission]` или внутри правила переводит раздел в режим только для чтения:
  регенерировать такой блок значило бы потерять чужие данные. Прочие ключи `config.toml`
  (провайдеры, модели, хуки, таймауты MCP) остаются байт-в-байт.
- **OpenCode** — ключ `permission` в `opencode.json` (глобальном и проектном): у инструмента
  уровень `allow` / `ask` / `deny`; задокументированы `edit`, `bash`, `webfetch`. У `bash` вместо
  одного уровня можно задать список шаблонов (`*` → `ask`, `git *` → `allow`,
  `git push *` → `deny`) — панель правит его строками «шаблон + уровень». Всё незнакомое внутри
  `permission` сохраняется как есть и показывается только для чтения; переопределения у отдельных
  агентов (`agent.*`) не трогаются вовсе.

## 5. Чат / ассистент

У Claude это полноценный чат: стриминг, вложения, ветвление, параллельные агенты, история.

🧪 у Codex, Gemini, Qwen Code, Continue, Goose, Kimi Code, OpenCode и Aider — **базовый ассистент**: один
вопрос, один ответ, без стриминга и вложений (`codex exec`, `gemini -p`, `qwen -p`, `cn -p`,
`goose run --no-session -t "<промпт>"`, `kimi -p`, `opencode run "<промпт>"`, `aider --message`).
Промпт всегда передаётся отдельным аргументом, без склейки в строку оболочки; у OpenCode он идёт
позиционным аргументом подкоманды `run` (стандартный ввод этот CLI не принимает). У Goose разовый
ответ запрашивается явно: `run` с `--no-session` не оставляет файла сессии, а промпт передаётся
через `-t`.

Ассистенты **Aider, OpenCode, Continue, Goose и Kimi Code собраны по документации и не проверены живым прогоном** — эти CLI на
машине разработки не установлены. У **Cursor** своего модельного API нет, ассистент недоступен.

## 6. Скрипты

Раздел **самой панели**: ваши файлы (`.mjs`, `.sh`, `.ps1`, `.py`) в папке `hooks/` каталога
панели. Ни CLI провайдера, ни его формат конфигурации здесь не участвуют, поэтому раздел работает
у всех. Claude-специфичны ровно две вещи и у остальных скрыты: **песочница** (она поднимает
изолированный Claude Code) и отметка **«вызывается хуком»**. Заготовки кода тоже подменяются: без
хуков предлагаются самостоятельные скрипты, а не каркасы хуков Claude.

## 7. Проекты

Реестр проектов общий, конфиг выбранного проекта — свой у каждого провайдера.

| CLI       | Что доступно в проекте                                                                                                                          |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude    | `CLAUDE.md`, `.mcp.json`, права в `.claude/settings.json`                                                                                       |
| Codex     | `AGENTS.md`, MCP в `.codex/config.toml`                                                                                                         |

| Qwen Code | `QWEN.md`, MCP + права + **хуки** в `.qwen/settings.json`, переменные в `.qwen/.env`, **скиллы** в `.qwen/skills/`                              |
| Continue  | каталог правил `<проект>/.continue/rules/*.md`, MCP в `.continue/mcpServers/mcp.json`, переменные в `.continue/.env`                            |
| Goose     | только `<проект>/.goosehints` — проектного `config.yaml` Goose не читает                                                                        |
| Kimi Code | `AGENTS.md`, MCP в `.kimi-code/mcp.json`, **скиллы** в `.kimi-code/skills/`; проектных прав и хуков нет — их CLI читает из одного `config.toml` |
| Cursor    | каталог правил `<проект>/.cursor/rules/*.mdc`, MCP в `.cursor/mcp.json`, права в `.cursor/cli.json`                                             |
| OpenCode  | `AGENTS.md`, MCP и права в `opencode.json`                                                                                                      |
| Aider     | `<проект>/.aider.conf.yml`: список `read` и `set-env`, как и глобально                                                                          |

Конфиг Aider по документации ищется в домашнем каталоге, **в корне git-репозитория** и в текущем
каталоге — в этом порядке, поздний перекрывает ранний. Правки идут теми же адаптерами, что и на
глобальном уровне: чужие ключи и комментарии целы, перед записью резервная копия, путь за пределы
каталога проекта запрещён.

## 8. Хуки

У **Claude** — его собственная модель: `PreToolUse`/`PostToolUse` с матчерами инструментов и
командами оболочки в `settings.json`.

У **OpenCode** — ключ `experimental.hook` в `opencode.json` (глобальном и проектном), событий
ровно два: **«файл изменён»** (`file_edited`) сопоставляет шаблон файлов со списком действий и
**«сессия завершена»** (`session_completed`) — просто список действий. Команда задаётся **списком
аргументов**, а не строкой для оболочки: первым программа, дальше аргументы по одному, поэтому
пробел внутри аргумента безопасен, а «`prettier --write`» одной строкой не сработает — панель
показывает это отдельными полями. Правится только этот ключ: прочие настройки, другие ключи
`experimental` и незнакомые события сохраняются и показываются только для чтения.

**Раздел только для чтения.** Ключ лежал в `experimental`, который OpenCode
объявляет нестабильным, — и он действительно исчез: `experimental.hook` больше не упоминается в
справочнике конфигурации, его нет в опубликованной схеме, а сам `experimental` в схеме закрыт для
чужих ключей, то есть такой ключ схема отвергает. Панель перестала его писать: писать в чужой
конфиг то, чего нет ни в документации, ни в схеме, — это гадание.

Что осталось: панель **показывает** то, что уже лежит в вашем файле (свои хуки вы не потеряете и
можете править их руками), а на попытку записи отвечает отказом с этой самой причиной.
Задокументированный способ повесить действие на событие теперь один — **плагины** (раздел 9), они
в панели есть. Опишут ключ обратно — раздел оживёт без переделки.

У **Qwen Code** хуки живут ключом корня `hooks` в `settings.json` — том самом файле, где панель уже
правит права и режим аппрувов (глобальный `~/.qwen/settings.json` и проектный
`<проект>/.qwen/settings.json`). Форма — событие → список групп, у группы необязательный `matcher`
и одно действие `{ "type": "command", "command": …, "timeout": … }`. **Таймаут в миллисекундах**
(по умолчанию 60 000). Событий восемнадцать (`PreToolUse`, `PostToolUse`, `SessionStart`,
`SubagentStop`, `PreCompact`, `Notification` и другие); у шести — `UserPromptSubmit`,
`MessageDisplay`, `Stop`, `StopFailure`, `TodoCreated`, `TodoCompleted` — матчера нет по
документации, и панель поле просто не показывает.

Сохранение — **поэлементное**: группа с двумя действиями, действие не типа `command`, чужое поле,
событие вне списка — и **это событие целиком** уходит в режим только для чтения (панель показывает
его как сырой JSON и никогда не переписывает), а остальные события правятся как обычно. Ключ
`disableAllHooks` панель только показывает предупреждением: включён — CLI не выполнит ни одного
хука, снимается он вручную.

У **Kimi Code** хуки — массив таблиц `[[hooks]]` в `~/.kimi-code/config.toml` (там же, где права).
Полей ровно четыре: `event`, необязательный `matcher` (регулярное выражение), `command` (строка для
оболочки) и `timeout` — **в секундах**, 1–600, по умолчанию 30. Событий шестнадцать; первые три —
`UserPromptSubmit`, `PreToolUse`, `Stop` — умеют заблокировать действие кодом выхода 2. Проектных
хуков у Kimi нет вовсе: проектного `config.toml` этот CLI не читает.

Разница с Qwen в защите: плоский массив TOML нельзя переписать частично, не потеряв чужие данные,
поэтому любое отклонение от задокументированной формы — незнакомое поле, событие вне списка,
таймаут за границами — переводит в режим только для чтения **весь раздел**, а не одну запись.
Запись хирургическая: заменяется только непрерывный регион `[[hooks]]`, комментарии и порядок
остальных ключей целы, пустой список этот регион удаляет.

## 9. Плагины

У **Claude** — расширения самой панели и маркетплейсы (обёртка над `claude plugin`).

У **OpenCode** — плагины его собственного CLI, два задокументированных способа:

- **Файлы** JS/TS в каталоге, который OpenCode грузит при старте: `~/.config/opencode/plugins/`,
  проектный `<проект>/.opencode/plugins/`. Панель ведёт их как файловый менеджер (список, включая
  подкаталоги, чтение, создание, правка, удаление); копия перед записью и удалением, каталог
  создаётся только при явном сохранении. Защита путей — как у правил Cursor.
- **Список npm-пакетов** ключом `plugin` в `opencode.json`, включая scoped `@org/name`.
  Устанавливать пакеты панель не умеет — только правит список. Записи «имя + объект настроек»
  схема допускает, но их формы документация не описывает: такие сохраняются как есть, только
  чтение.

У **Kimi Code** плагины ставятся и включаются командой `/plugins` внутри самого CLI, поэтому раздел
в панели **только для чтения** — это не пробел, а решение. Панель читает каталог
`~/.kimi-code/plugins/managed/<id>/` и манифест каждого плагина (`kimi.plugin.json` либо
`.kimi-plugin/plugin.json`) и показывает список: имя, версию, описание и что именно плагин приносит
— скиллы, скилл на старте сессии, MCP-серверы, сколько хуков объявляет, есть ли команды. Рядом —
путь к реестру `~/.kimi-code/plugins/installed.json`. Формы этого реестра документация не
описывает, а править состояние в обход `/plugins` — гадание: на попытку записи раздел отвечает
отказом с этой причиной. Битый манифест не ломает список — такой плагин показан с пометкой об
ошибке.

## 10. Скиллы

У **Claude** — богатый раздел: папка на скилл с деревом файлов, включение переносом в
`skills-disabled/`, группы, библиотека шаблонов.

У **OpenCode** понятие то же (папка со `SKILL.md` и YAML-шапкой), но каталоги и поля свои:
`~/.config/opencode/skills/<имя>/SKILL.md`, проектный `<проект>/.opencode/skills/<имя>/SKILL.md`.
Панель правит два обязательных поля шапки — `name` и `description`; `license`, `compatibility`,
`metadata` и любые чужие сохраняются как есть, только чтение. `name` обязан совпадать с именем
папки и подчиняться правилам (1–64 символа, строчные латинские, цифры, одиночные дефисы, без
дефиса по краям и без `--`) — проверка до записи. Путь обязан иметь форму `<имя>/SKILL.md` внутри
каталога, папки создаются только при явном сохранении.

Полезно знать: OpenCode грузит скиллы ещё и из `~/.claude/skills` и `~/.agents/skills`, поэтому
ваши скиллы Claude работают в нём без переноса — панель сообщает об этом и в эти каталоги ничего
не пишет.

У **Qwen Code** и **Kimi Code** формат тот же — папка со `SKILL.md` и шапкой `name` +
`description`, — меняются только каталоги: `~/.qwen/skills/` и `<проект>/.qwen/skills/` у Qwen,
`~/.kimi-code/skills/` у Kimi (проектный — `<проект>/.kimi-code/skills/`). Kimi, как и OpenCode,
подхватывает общий каталог `~/.agents/skills` — панель говорит об этом и туда не пишет. Отличие
одно: у Kimi документация ограничивает `description` 240 символами, и панель проверяет именно эту
границу. Имя скилла панель держит по самому строгому из трёх правил (строчная латиница, цифры,
одиночные дефисы) — такое имя валидно в любом из этих CLI, и переносить скилл между ними не
придётся переименовывать.
